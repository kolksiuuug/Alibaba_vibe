Прототип цифрового кредитного конвейера для малого и микробизнеса. Трек «Умный кредитный кабинет предпринимателя», Альфа-Будущее Хакатон 2026.

## 1. Жёсткие ограничения

   - машина с 8 ГБ ОЗУ, без GPU;
   - Ollama — только профиль `llm` в compose или отдельный запуск вне Docker, описанный в README.

9. **Обязательные артефакты** (раздел 10) не удалять. Обновлять их в том же коммите, что и код, который они описывают.
10. **Вне скоупа кейса:** новостная лента (фраза в ТЗ относится к другому треку), регистрация клиентов. Не добавлять.

## 2. Что строим (MVP)

Одно веб-приложение с двумя ролями.

**Предприниматель (`client`)** — уже клиент банка, данные компании известны, регистрации нет:

1. Вход в демо-профиль: выбор из списка демо-компаний, без паролей и кодов.
2. Подбор продукта: цель, сумма, срок → 1–3 продукта с предварительными условиями и ежемесячным платежом.
3. Заявка: поля компании предзаполнены, проверка полноты, черновик сохраняется.
4. Трекер заявки: статус, этапы проверки, что происходит и что делать дальше.
5. Ответ на дозапрос банка.
6. Предложение: условия, график платежей, объяснение решения по факторам. Можно принять или отклонить.
7. Подписание кодом в UI → выдача (симуляция).
8. Центр уведомлений в продукте.

**Кредитный аналитик (`analyst`)** — в том же приложении:

1. Очередь заявок с фильтром по статусу.
2. Карточка заявки: данные, результаты проверок, скоринг с разбивкой по факторам, рекомендация движка.
3. Решение по ручному рассмотрению: одобрить, изменить условия, запросить информацию или отказать. Комментарий обязателен.
4. Журнал переходов статуса.

**Не делаем:** регистрацию, новостную ленту, мобильное приложение, реальные интеграции, почту и СМС, посткредитное обслуживание.

## 6. Доменная модель

Основные сущности (детали — `docs/data-model.md`):

- `Company` — ИНН, ОГРН/ОГРНИП, тип (`ip` | `llc`), ОКВЭД, дата регистрации, месячные обороты по счёту (синтетика).
- `User` — роль (`client` | `analyst`), `company_id` для клиента.
- `Product` — код, название, цели, мин./макс. сумма и срок, спред к ключевой ставке, нужен ли залог или поручительство.
- `Application` — компания, продукт, сумма, срок, цель, данные анкеты (JSON), `status`, этапы конвейера (`pipeline_steps`) для таймлайна в UI.
- `PipelineJob` — `application_id`, `state` (`queued` | `running` | `done` | `failed`), `attempts`, `run_after`, `heartbeat_at`, `last_error`.
- `CheckResult` — источник (`bki` | `egrul` | `fns`), ответ, статус, время.
- `ScoringResult` — балл, грейд A–E, факторы (`code`, `value`, `points`, `explanation_ru`), сработавшие стоп-факторы.
- `Decision` — исход, предложенные сумма, срок, ставка и платёж, причины, кто решил (`engine` | `analyst`), комментарий.
- `InfoRequest` — что запрошено и ответ клиента.
- `Signature`, `Disbursement` — симуляция.
- `Notification` — уведомления в продукте.
- `AuditEvent` — смена статуса: `from`, `to`, `actor`, `reason`, `at`. Пишется при каждом переходе.

## 7. Машина состояний и конвейер

Коды статусов одинаковые в БД, API, UI и документации. Русские подписи — только в UI-словаре.

| Код | UI | Кто переводит дальше |
| --- | --- | --- |
| `draft` | Черновик | клиент |
| `submitted` | Подана | система |
| `checking` | Проверка и скоринг | система |
| `info_requested` | Нужна информация | клиент |
| `manual_review` | Ручное рассмотрение | аналитик |
| `offer` | Предложение (одобрение или контрпредложение, флаг `is_counter`) | клиент |
| `accepted` | Принято | клиент (подпись) |
| `signed` | Подписано | система (выдача) |
| `issued` | Выдано | — |
| `rejected` | Отказ | — |
| `declined` | Отклонено клиентом | — |
| `cancelled` | Отменена клиентом | — |

Разрешённые переходы (единственный источник — `app/domain/state_machine.py`):

```
draft          -> submitted (client), cancelled (client)
submitted      -> checking (system)
checking       -> info_requested | manual_review | offer | rejected (system)
info_requested -> checking (client: ответил на дозапрос), cancelled (client)
manual_review  -> offer | rejected | info_requested (analyst, комментарий обязателен)
offer          -> accepted | declined (client)
accepted       -> signed (client: код подписи в UI)
signed         -> issued (system: мок выдачи)
```

**Правила переходов:**
- Статус меняется только через `services/transitions.py`. Прямое присваивание `application.status` запрещено.
- Каждый переход в одной транзакции пишет `AuditEvent` и `Notification` клиенту.
- Недопустимый переход → HTTP 409 (problem+json).
- Повтор того же действия в уже целевом статусе возвращает 200 с текущим состоянием, то есть переходы идемпотентны.

**Конвейер (очередь в PostgreSQL, без Redis):**
- `submit` и `info-response` в одной транзакции меняют статус и создают `PipelineJob(queued)`.
- `worker` раз в секунду забирает задачу через `SELECT … FOR UPDATE SKIP LOCKED` и проходит шаги, сохраняя прогресс в `pipeline_steps`. Шаги: валидация → ЕГРЮЛ/ЕГРИП, ФНС, БКИ → скоринг → решение. Каждый шаг идемпотентен.
- Если `heartbeat_at` устарел больше чем на 60 с, задача возвращается в очередь. Не больше 3 попыток, после них заявка уходит в `manual_review` с причиной.
- Если мок недоступен после ретраев, заявка уходит в `manual_review` с причиной, а не падает.
- Выдача после подписи (`signed → issued`) — тоже задача воркера.
- `PIPELINE_STEP_DELAY_MS` (по умолчанию 700) — задержка шагов, чтобы на демо было видно движение статуса. В тестах 0.

## 8. Скоринг и кредитное решение (`app/scoring/`)

Детерминированные правила, никакого ML. Все веса и пороги лежат в `scoring/config.yaml` и описаны в `docs/scoring.md`. Скоринг даёт оценку риска, а итог определяет `decision_engine.py` с учётом продукта, суммы, срока и проверок.

1. **Стоп-факторы → `rejected`.** Компания не действующая по ЕГРЮЛ/ЕГРИП (ликвидация, банкротство). Текущая просрочка больше 90 дней в БКИ. Налоговая задолженность выше порога. Бизнесу меньше 6 месяцев.
2. **Неполные данные → `info_requested`.** Не хватает обязательных для продукта полей или документа, например данных о залоге для инвестиционного кредита.
3. **Скоринговая карта.** Сумма баллов по факторам, каждый фактор возвращает баллы и объяснение на русском:
   - возраст бизнеса;
   - среднемесячный оборот;
   - стабильность оборотов (коэффициент вариации);
   - долговая нагрузка (платежи / оборот);
   - кредитная история (макс. просрочка за 24 мес., число просрочек);
   - налоговая дисциплина;
   - запрошенная сумма / годовой оборот;
   - залог или поручительство;
   - отраслевой риск по ОКВЭД.

   Сумма → грейд A–E.
4. **Решение по грейду:**
   - A/B: сумма ≤ лимита → `offer`; иначе `offer` с `is_counter=true` (сумма = лимит, при необходимости срок длиннее);
   - C → `manual_review`;
   - D → контрпредложение с уменьшенной суммой, если платёж проходит по долговой нагрузке, иначе `rejected`;
   - E → `rejected`.
5. **Лимит** = min(макс. сумма продукта, k(грейд) × среднемесячный оборот × f(срок)), при условии платёж / оборот ≤ порога.
6. **Ставка** = `KEY_RATE` + спред продукта + надбавка за грейд. Платёж аннуитетный. Условия должны быть рыночными.
   - `KEY_RATE` задаётся в env, по умолчанию 14.0 (ключевая ставка ЦБ на 23.10.2026). Если ставка изменится, обнови значение.
7. **Объяснимость.** Клиент видит 3–5 главных факторов простыми словами. Аналитик видит все факторы с баллами.
8. Логика не должна быть заточена под демо-компании: эксперты могут прогнать свои синтетические сценарии.

Каждая ветка решения покрыта unit-тестом.

## 9. Синтетические данные (`seed/`)

- **Сид применяется автоматически** в `entrypoint.sh`, если БД пустая. Пересоздать — `make seed`.

## 11. API (Flask + flask-smorest)

- REST, префикс `/api/v1`, JSON, `snake_case`. Blueprints smorest, валидация и сериализация — Marshmallow-схемы из `app/api/schemas/`.
- Swagger UI — `/api/docs`, схема — `/api/openapi.json`. Настройки: `OPENAPI_URL_PREFIX="/api"`, `OPENAPI_SWAGGER_UI_PATH="/docs"`. После изменения API — `make openapi`, затем перегенерировать типы фронта.
- Ошибки — `application/problem+json` (RFC 7807) через свой обработчик в `app/api/__init__.py`: 409 на недопустимый переход, 422 на валидацию, 403 на чужую заявку.
- Авторизация: `Authorization: Bearer <token>`. Токен подписан `itsdangerous` (уже есть в зависимостях Flask), в нём `user_id` и `role`. Декоратор `@require_role("client" | "analyst")`. Клиент видит только заявки своей компании.
- Бизнес-логика — только в `services/` и `scoring/`. Роутеры вызывают сервисы и сериализуют ответ.

## 12. Frontend (`frontend/`)

- React SPA, собирается в образе `nginx`, ходит в API по относительному пути `/api/v1`.
- Типы API генерируются из `docs/openapi.yaml` (`npm run gen:api`). Руками типы ответов не пишем.
- На каждом экране понятно, что сейчас происходит и что делать дальше. Пользователь не банкир: без внутренних терминов, с подсказками.
- Статусы и этапы — из словаря `src/shared/statuses.ts`. Коды совпадают с backend.
- Пока заявка в `submitted` или `checking`, статус обновляется опросом раз в 2 секунды (`refetchInterval` TanStack Query).
- У смоделированных шагов (подпись, выдача) плашка «Симуляция».
- Переключатель ролей и выход видны всегда, чтобы эксперту было удобно пройти оба сценария.
- Фирменный красный Альфы и логотип использовать можно, но не обязательно. Дизайн-система банка не требуется.

## 13. Enterprise-практики (их оценивают)

- Слои: `api → services → domain / scoring`; `models` и `adapters` за интерфейсами. В роутерах нет бизнес-логики.
- Адаптеры к внешним сервисам:
  - httpx с таймаутом 3 с, 2 ретрая с backoff;
  - понятный fallback — `manual_review`, а не 500.
- Надёжная обработка: очередь в БД, `SKIP LOCKED`, heartbeat, ограниченные попытки. Переживает рестарт `worker` и `app`.
- Конфигурация через env, классы `DevConfig` / `TestConfig` / `ProdConfig`. Секреты не в репозитории.
- Миграции Flask-Migrate. Никаких `db.create_all()` вне тестов.
- Структурные JSON-логи с `request_id`. ИНН, телефоны и ФИО в логах маскируются.
- Healthchecks в compose, сервисы ждут готовности БД.
- Безопасность зависимостей: перед сдачей прогнать `pip-audit` и `npm audit`, критичное исправить.
- Тесты:
  - unit — скоринг, решение, машина состояний;
  - API — пять сценариев на pytest-flask против тестовой БД, воркер вызывается синхронно;
  - UI (желательно) — те же пять сценариев на Playwright в `frontend/e2e/` против `http://localhost:8080`; Playwright только в `devDependencies`, в образ не попадает;
  - `make test` проходит с нуля.
- LLM-адаптер (если включён): таймауты, проверка пустого ответа, fallback на шаблонный текст. Ассистент только объясняет и подсказывает, решений не принимает.
