# Допущения и упрощения

Прототип работает автономно: внешние системы не вызываются, все данные синтетические. Ниже перечислено, что смоделировано и почему.

## Внешние интеграции

Все обращения идут через адаптеры `app/adapters/` (интерфейсы — `base.py`) в контейнер `mocks`. Параметры адаптеров: httpx, таймаут 3 с, 2 ретрая с экспоненциальным backoff (0,2 с и 0,4 с). Ответы 4xx не повторяются. Если система недоступна после ретраев, заявка уходит в `manual_review` с причиной `<источник>_unavailable`, а не падает с ошибкой 500.

| Система | Эндпоинт мока | Что моделируется | Упрощение |
| --- | --- | --- | --- |
| Бюро кредитных историй | `GET /bki/report?inn=` | действующие кредиты, ежемесячные платежи, текущая и максимальная просрочка за 24 мес., число просрочек | один отчёт вместо отчётов нескольких бюро; нет кредитного рейтинга бюро |
| ЕГРЮЛ / ЕГРИП | `GET /egrul/{inn}` | статус (действует, ликвидация, банкротство), дата регистрации, ОКВЭД | нет учредителей, адресов и истории изменений |
| ФНС «Прозрачный бизнес» | `GET /fns/transparent-business/{inn}` | налоговая задолженность, опоздания с уплатой за 12 мес., режим налогообложения, численность | вместо выписки из нескольких реестров ФНС — один ответ |
| Электронная подпись | `POST /esign/sign` | подписание договора кодом, который показывается и вводится в интерфейсе | нет сертификата ЭП и криптографии; плашка «Симуляция» |
| АБС банка | `POST /abs/disbursements` | зачисление кредита на расчётный счёт | мгновенное зачисление; повтор с тем же `idempotency_key` возвращает ту же выдачу |

Демо-компании отвечают данными из `mocks/data/*.json`. Для любого другого корректного ИНН (10 или 12 цифр) мок строит детерминированный ответ от SHA-256 ИНН, поэтому эксперты могут прогнать свои синтетические сценарии. Для демонстрации сбоев есть `MOCKS_FAILURE_RATE` (доля случайных ответов 503) и `GET /admin/fail?service=bki` (выключить: `&enabled=false`).

## Данные

- Компании, люди, ИНН и ОГРН вымышлены. В ИНН и ОГРН используется несуществующий код региона `00`, поэтому номера не совпадут с реальными организациями.
- Обороты по расчётному счёту — 12 месяцев синтетических данных в `seed/demo_companies.json`; в реальности банк видит их по своим счетам клиента.
- Клиент уже обслуживается в банке, поэтому регистрации нет: вход — выбор демо-профиля.

## Скоринг и решение

- Детерминированные правила без машинного обучения (`docs/scoring.md`). Пороги откалиброваны вручную под реалистичные профили малого бизнеса, а не по статистике дефолтов.
- Долговая нагрузка считается от оборота, а не от прибыли: прибыль малого бизнеса банку обычно неизвестна, а оборот по счёту виден.
- Ключевая ставка — параметр `KEY_RATE` (по умолчанию 14,0 на 23.10.2026), а не запрос к ЦБ.

## Конвейер

- Очередь — таблица `pipeline_jobs` в PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED`), без Redis и брокера сообщений.
- Задача с устаревшим heartbeat (больше 60 с) возвращается в очередь. Делается не больше 3 попыток с паузой 5 с × номер попытки, после этого заявка уходит в `manual_review` с причиной `pipeline_failed`.
- Результаты проверок по заявке переиспользуются. После ответа на дозапрос внешние системы повторно не вызываются: их данные за минуты не меняются.
- `PIPELINE_STEP_DELAY_MS` (по умолчанию 700 мс) искусственно замедляет шаги, чтобы на демо было видно движение статуса.
- Если выдача через АБС не удалась после всех попыток, заявка остаётся в статусе `signed`, а клиент получает уведомление о задержке. В реальном банке такую заявку разбирал бы операционный отдел.

## Вход, подпись и уведомления

- **Демо-вход без пароля.** Клиент уже обслуживается в банке, поэтому регистрации нет. Профиль выбирается на странице входа. Токен подписан `itsdangerous`, ключ `SECRET_KEY` по умолчанию публичный и подходит только для демо; `docker-compose.prod.yml` требует свой.
- **Подпись кодом в интерфейсе.** Код из 6 цифр показывается на странице и вводится там же: SMS, звонки и мессенджеры не используются. Код живёт 10 минут, даётся 5 попыток, в БД хранится только солёный хеш. Подписывается SHA-256 условий предложения. Шаг помечен плашкой «Симуляция».
- **Уведомления только в продукте.** На каждый переход статуса клиенту пишется уведомление в центр уведомлений (колокольчик в шапке). Email и SMS не отправляются.
- **Выдача** — мгновенное зачисление через мок АБС, плашка «Симуляция».

## Интерфейс

- Desktop-first, адаптив не делался (CLAUDE.md, раздел 1.1).
- Статус обновляется опросом раз в 2 секунды, пока заявка в `submitted`, `checking` или `signed`. WebSocket не нужен: события редкие, опрос проще и надёжнее.
- Аналитик видит все заявки, кроме черновиков. Распределения заявок между аналитиками нет — в прототипе аналитик один.

## LLM

В проверяемой версии LLM не используется: `LLM_ENABLED=false`, основной сценарий от неё не зависит. Объяснения решения строятся детерминированно из факторов скоринга.

## Безопасность зависимостей

Проверка от 25.10.2026: pip-audit 2.10.1 по `requirements.txt` и `mocks/requirements.txt` с ключами из `make audit`, npm audit.

25.10.2026 по решению команды обновлены Flask 3.1.2 → 3.1.3 (исправляет CVE-2026-27205: нет `Vary: Cookie` при обращении к `session`) и python-dotenv 1.0.1 → 1.2.2 (исправляет CVE-2026-28684: `set_key()`/`unset_key()` следуют по симлинкам). Зависимости Flask 3.1.3 те же, что у 3.1.2, остальные пины в lock-файлах не изменились. pip-audit по этим пакетам уязвимостей больше не находит.

Оставшиеся уязвимости:

| Пакет | Уязвимость | Почему не затрагивает проект |
| --- | --- | --- |
| pytest 8.3.3 | CVE-2025-71176 (PYSEC-2026-1845, исправлено в 9.0.3): каталоги `/tmp/pytest-of-*` на многопользовательском хосте | pytest есть в образе `app` только для `make test`, приложение его не импортирует; тесты запускаются в одноразовом контейнере |
| react-router-dom 6.30.6 | moderate: open redirect через `\` в `<Link>`/`useNavigate`; SSR-гидрация | навигация только по внутренним путям, SSR нет |

npm audit находит только уязвимости уровня moderate (`npm audit --audit-level=high` проходит). pytest оставлен на 8.3.3 сознательно: переход на 9.x — мажорное обновление тестового стека накануне сдачи, а уязвимость не затрагивает запуск тестов в контейнере.

## Логи

Логи приложения и воркера — JSON с `request_id`; ИНН, ОГРН, телефоны и ФИО маскируются. Служебные строки Gunicorn и Alembic при старте остаются в их стандартном текстовом формате.
